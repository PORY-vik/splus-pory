# splusjava

**Ported and maintained by Pory Viking.**

A Java 7 port of [SPlusthon](https://github.com/shayanheidari01/SPlusthon) (the Python MTProto
client for [Soroush Plus](https://web.splus.ir)). Ships as a single jar with **no external
dependencies** (only the JDK/Android standard library), so it drops straight into a Sketchware
project as a library `.jar`.

## What's in this drop

| Package               | What it does |
|------------------------|---------------|
| `splusjava.tl`         | Generic TL codec: the whole layer 182 API schema is parsed at runtime from `SchemaData` (generated by `tools/gen_schema.py`), so there is **no per-method generated class** - you build/read requests with `TLObject`. |
| `splusjava.crypto`     | AES-IGE, AES-CTR, RSA (raw, PKCS#1-less as MTProto needs it), Pollard-rho factorization, the server's public keys. |
| `splusjava.mtproto`    | `AuthKey`, `MTProtoState` (message encryption/decryption + all the security checks), `Authenticator` (the key-exchange handshake), `MTProtoSender` (the request/response loop, containers, acks, salt/bad_msg recovery). |
| `splusjava.net`        | A dependency-free WebSocket client (`WebSocketClient`) + the obfuscated2 transport (`ObfuscatedIo`) + abridged packet framing (`AbridgedCodec`), combined in `SoroushConnection` - matches SPlusthon's `ConnectionWebSocket` byte for byte. |
| `splusjava.Session`    | Where to connect + the auth key, as a portable string. **Compatible with SPlusthon's `StringSession`** - you can move a logged-in session between the Python and Java libraries. |
| `splusjava.SoroushClient` | The class you actually use: `connect()`, `invoke(TLObject)`, `disconnect()`, plus convenience methods (below). |
| `splusjava.Peers`      | Turns a `User`/`Chat`/`Channel` (or a `Peer` + the `users`/`chats` lists next to it) into the `InputPeer`/`InputUser`/`InputChannel` most calls expect. |
| `splusjava.Files`      | Chunked `upload.saveFilePart`/`upload.getFile` - upload a `byte[]` and get an `InputFile`, or download a document/photo to a `byte[]`. |
| `splusjava.crypto.SrpPassword` | Two-step-verification (SRP) password proof for `auth.checkPassword` - also exposed as `SoroushClient.checkPassword(password)`. |
| `splusjava.UpdatesTracker` (internal) | Tracks pts/qts/date/seq and calls `updates.getDifference` to fill any gap (missed updates), automatically - see `SoroushClient.setUpdateListener`/`getUpdatesState`/`syncUpdates`. |

## Quick start

```java
Session session = Session.parse(savedSessionStringOrEmpty);
SoroushClient client = new SoroushClient(session);
client.connect();                              // does the key exchange the first time only
String sessionString = session.save();         // persist this - skips the key exchange next run

// --- login (skip if session already has an authorized key) ---
String hash = client.sendCode("+989121234567");
try {
    client.signIn("+989121234567", hash, "12345");
} catch (RpcException e) {
    if (e.is("SESSION_PASSWORD_NEEDED")) {
        client.checkPassword("my2FApassword");     // SRP, only if the account has a password set
    } else {
        throw e;
    }
}

// --- everyday calls, with the high-level helpers ---
client.sendMessage("SomeUsername", "hello from Java");                 // resolves + sends
TLObject peer = client.resolvePeer("SomeUsername");                    // resolve once, reuse the InputPeer
client.sendDocument(peer, fileBytes, "report.pdf", "application/pdf", "here you go");
TLObject dialogs = client.getDialogs(50);
TLObject history = client.getHistory(peer, 20);
client.markRead(peer, 0);
client.setUpdateListener(new MTProtoSender.UpdateListener() {
    public void onUpdate(TLObject update) {
        // called for every server-pushed update (new messages, edits, status...), gap-checked and
        // resynced automatically - see "Updates and auto-reconnect" below
    }
});

// --- or call anything in the API directly - every field name matches the TL schema exactly ---
TLObject result = (TLObject) client.invoke(TLObject.of("messages.sendMessage",
        "peer", peer, "message", "hello from Java", "random_id", Long.valueOf(System.nanoTime())));
```

For anything not covered by a convenience method, build the request by hand with
`TLObject.of("methodName", "field", value, ...)` - the field names are exactly the ones in the TL
schema (see `splusthon_generator/data/api.tl` in the original repository, or call `TLObject.create(name)`
with a bad field to get the full parameter list in the exception message). The result of `invoke()`
is a `TLObject` (read fields with `.getString()`, `.getLong()`, `.getObject()`, `.getList()`...), a
`java.util.List`, or a boxed primitive, depending on what the method returns.

See `examples/SendMessageExample.java` for a runnable end-to-end example (login incl. 2FA, resolve,
send a message, read a result).

## Updates and auto-reconnect

- **Incoming updates**: `client.setUpdateListener(listener)` gets called for everything the server
  pushes (new messages, edits, read receipts...). Internally, every update is checked against the
  tracked `pts`/`seq` (`client.getUpdatesState()`); if a gap is detected (or after a reconnect) the
  library calls `updates.getDifference` itself and delivers the recovered messages/updates to your
  listener in order, so you don't need to think about this - see `splusjava.UpdatesTracker` if you do.
  Each channel/supergroup's own, independent pts sequence is tracked the same way, via
  `updates.getChannelDifference` - this needs the channel's `access_hash`, which is learned
  automatically from `client.getDialogs()`/`client.resolveUsername()` or from any update that happens
  to mention the channel; call `client.learnChats(chatsList)` yourself if you got a `Channel` object
  some other way. Until a channel's access_hash is known, a gap on it is logged and left unresolved
  (rather than guessed at) - this is now the one edge case left, down from "not tracked at all".
- **Auto-reconnect**: on an unexpected disconnect the client reconnects automatically (exponential
  backoff, capped at 30s), reusing the existing auth key - no new login - and resyncs updates once
  back. Call `client.setAutoReconnect(false)` to turn this off, or `client.setDisconnectListener(...)`
  to be notified either way (`error == null` means you called `disconnect()` yourself).

## Building

Needs a JDK (javac) and Python 3 (only for the two small code-gen/packaging scripts, not at runtime).

```sh
./build.sh          # -> dist/splusjava.jar
./build.sh test      # also compiles and runs the unit test suite
```

The jar's class files are patched to major version **51 (Java 7)** even though javac itself only
emits 52+ on modern JDKs (see `tools/make_jar.py`) - old Android/Sketchware toolchains (`dx`) reject
anything newer.

To use a newer/updated copy of the original SPlusthon repository (new API layer, new server keys),
re-run the generator and rebuild:

```sh
python3 tools/gen_schema.py /path/to/SPlusthon-main
./build.sh
```

## What has been verified, and what has not

This port was built and tested **offline**, without network access to Soroush's servers. What that
means concretely:

- **Byte-for-byte verified against the real SPlusthon Python code** (139 automated checks, see
  `src/test/java/splusjava/*Tests.java` and the `*Vectors.java` files generated from the Python
  library - `./build.sh test` reruns them): the TL binary codec (every field type, flags, vectors,
  nested objects, gzip_packed) for ~30 real API requests/objects, AES-IGE, RSA key fingerprints and
  encryption, Pollard-rho factorization, the `generate_key_data_from_nonce` key derivation, `AuthKey`
  id/aux-hash/new-nonce-hash, `MTProtoState` message encryption **and** decryption (including its
  security checks: wrong auth key, short packets, replay), the obfuscated2 transport header/stream
  cipher, and the abridged packet framing.
- **Written carefully but not exercised against a live server**: the WebSocket handshake
  (`net.WebSocketClient`), the full `Authenticator.authenticate()` handshake sequence (each step's
  request/response shape and math is right, per the checks above, but the three network round trips
  together have not run against `im-server.splus.ir`), and `MTProtoSender`'s handling of containers,
  `bad_server_salt`/`bad_msg_notification` recovery, and update dispatch.
  SRP two-step-verification password proof (`SrpPassword.computeCheck`, wired into
  `SoroushClient.checkPassword`) is also checked this way against the Python library's own
  `password.compute_check`, PBKDF2-HMAC-SHA512 included.
  Update-gap recovery (`UpdatesTracker`), common and per-channel alike, is checked with an offline
  scripted-server test (no reference Python output exists to diff against here, so it instead verifies
  delivery order, no-duplicates and no-drops across a scripted gap - see `UpdatesTests.java` and
  `ChannelUpdatesTests.java`).
- **Not implemented**: MTProxy/plain-TCP transports (only the WebSocket transport Soroush Plus
  actually uses is implemented).

In short: the cryptography and the wire format are solid (checked against the real library's own
output), and the full flow (connect, login, send/receive messages) has now been confirmed working
against the live server. Update-gap recovery and auto-reconnect are new and have only been exercised
with a scripted fake server offline - if you notice missed updates after a long disconnect or a flaky
reconnect, that's the first place to look. Please run `./build.sh test` after any change.
